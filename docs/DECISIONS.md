## 2026-10-23 · 服务端保持无状态：授权码用校验位、题目用签名

**结论**：后端不引入数据库，也不存任何会话数据。三样东西全部用 HMAC 自包含：

| 凭证 | 格式 | 校验方式 |
|---|---|---|
| 授权码（8 位，线下售卖） | 7 位随机 + 1 位校验位 | `HMAC(LICENSE_SECRET, 前7位)` 首字节取模 |
| `host_token` | `{ lic, iat, exp }` + 签名 | 验签 + 看 `exp`（一年） |
| `question_id` | 题目 + 正确答案 + 作答前状态快照 + 签名 | 验签 + 过期时间（出题日 + 48h） |

**原因**

- 「无数据库」是既定架构（数据在用户飞书表里，我们不托管）；为身份校验引入数据库，等于把一条用户数据链重新挂回服务端。
- 题目签名里带**状态快照**，`submit` 不需要读任何存储就能算新状态；重复提交返回同一组 `updates`，天然幂等。
- 发码变成一次离线计算（`scripts/license-gen.ts`），不用维护码表。

**代价（明确接受）**

- 授权码**不能单独吊销**：只能轮换 `LICENSE_SECRET`，同时让所有旧码失效（MVP 可接受，用户量上来后需要真正的码表）。
- 会话数据只存在进程内存里：服务重启会丢「一键创建应用」的会话，用户重新点一次链接即可。
- 授权码长度固定 8 位、无期限字段，期限完全由激活时签出的 `host_token` 承载。

**实现**：`src/lib/token.ts`、`docs/API_IMPLEMENTATION.md` §2。

## 2026-10-23 · MVP 题面用确定性模板，LLM 润色默认关闭

**结论**：`/api/review/today` 的题面由**确定式模板**生成（掩码来源原句 / 释义提示），不调用大模型；`model` 字段照常校验接收，但默认不参与出题。LLM 润色留开关（`READLOOP_QUESTION_LLM=1`），失败自动回退模板。

**原因**

- 出题的**答案与判分**必须由代码决定（ARCHITECTURE §2.3），题面只是措辞；模板已经能产出可用的选择题与输入式填空题。
- 少一个网络依赖就少一类失败：模型超时 / Key 失效 / 输出不合格式都不该让「今天的题出不来」。
- 同样输入 + 同一天返回同一批知识点，模板让题面也可复现，便于自测。
- 生成式练习（cloze）不靠模型也成立：答案就是知识点本身。

**影响**

- 与 `ARCHITECTURE.md` §5.5「题面由 LLM 生成」的表述有偏差：**模型只影响措辞，暂不影响产品可用性**。
- `model` 配置仍是接口必填项（保留 BYOK 口径），但当前实现不因此产生费用。
- 需要同步更新 Store 的 `references/api.md` 与 SKILL 说明。

## 2026-10-23 · 插件凭证走「配对码自取」，Secret 不进宿主上下文

**结论**：一键创建出的 `app_secret` **不经过宿主的对话上下文**。流程是：插件显示 6 位配对码 → 用户把码交给宿主 → 宿主调 `POST /api/setup/app/pair` 只做绑定 → 插件用 `GET /api/setup/app/pair?code=` 一次性取走凭证。

**原因**

- 宿主是模型，凭证一旦出现在对话里就会进入上下文、日志、历史记录，等于泄露。
- 让用户手抄 App Secret 进插件设置，是初始化里最容易出错、也最像「开发者工具」的一步。

**影响**

- `pair` 的 POST 与 GET 语义不同：POST（宿主鉴权）只绑定，GET（无鉴权，靠一次性 6 位码）才返回凭证。
- 6 位码 + 10 分钟 TTL + 每会话 20 次尝试上限，MVP 可接受；后续可加设备指纹。
- `status` 接口仍保留一次性返回 `app_secret` 的能力（给兜底手动路径），但 SKILL 文档应引导走配对码。

## 2026-10-23 · 初始化用 `registerApp` 一键创建用户应用

**结论**：用户不需要进飞书开发者后台。Skill 第 3 步调后端跑 `registerApp`，用户只点一个链接、在飞书里点「同意」，就在**他自己的组织里**创建了一个属于他的自建应用；随后用三项校验确认能读能写。

**为什么改掉「手动创建」**

手动路径要 7 步（建应用、开权限、发布版本、加成协作者、填凭证…），约 10 分钟，且最容易漏「发布版本」和「加成可编辑」。对付费产品来说，初始化卡住 = 退款。

**发起方应用**：`cli_aa51d940d7381c06`

- 只负责「发起创建」，拿不到用户任何数据
- 需要 `application:application:self_manage`、`application:application:patch`
- 被创建的应用归属**用户**（`createOnly: true`，在用户组织内）
- 参考实现：TeamingBot 的 `appRegistrationStore.ts`，同一套 SDK 流程（Device Grant）

**三项校验**（人工流程里容易漏的，代码里补上）

| 检查 | 覆盖的问题 |
|---|---|
| 换 `tenant_access_token` | 凭证错 |
| 读表 + 列字段 | 没加成协作者 / 没开 `bitable:app` / 模板不全 |
| 写一条记录再删 | 只给「可阅读」没给「可编辑」 |

**Secret 处理**

- 创建成功后由后端**一次性**交给 Skill / 插件，服务端不落库
- 隐私政策需写明：创建过程中 App Secret 短暂经过服务端，交付后即丢弃

**影响**

- 后端新增 `/api/setup/app/start`、`/api/setup/app/status`
- Skill 第 3 步改为一键流程，手动 7 步降级为兜底
- 插件设置支持「配对码」拉取凭证，避免用户复制密钥

## 2026-10-23 · 插件写入走「用户自建飞书应用」，后端不接触表格

**结论**：Chrome 插件用**用户自己创建的飞书自建应用**（App ID + Secret）直连 `open.feishu.cn` 写表；宿主的 Skill 继续用自己的飞书能力读写。后端服务始终不持有任何飞书凭证、不接触用户表格。

**背景（这是架构里唯一的洞）**

宿主能读写自己的表，但**插件在用户浏览器里，拿不到宿主的飞书能力**。而收据必须实时落到用户自己的表里。

**评估过的方案**

| 方案 | 结论 |
|---|---|
| 飞书多维表格自动化「Webhook 触发」 | ❌ 是**增值付费功能**，不采用 |
| 我们的飞书应用 + 用户 OAuth，后端代写 | ❌ 我们的凭证能读所有用户的表 ⇒ 等于托管数据，与「数据归用户」冲突 |
| 延迟同步（后端暂存 → 宿主落表） | ❌ 有延迟，且需要暂存用户内容、隐私条款要改 |
| **用户自建应用 + 插件直连** | ✅ **采用** |

**为什么采用**

- 免费（自建应用不收费，只有 Webhook 等增值功能收费）
- 实时：插件靠 `host_permissions` 直连 `open.feishu.cn`，不受 CORS 限制，不需要后端中转
- 我们始终没有访问权：应用在用户手上，用户把它加成表格协作者
- 同类产品已有成熟做法：[feishu-web-clipper](https://github.com/EConG37/feishu-web-clipper)、[job-tracker-extension](https://github.com/Zheyi-D/job-tracker-extension)

**影响**

- 初始化第 3 步变长：建表后要引导用户创建自建应用（约 10 分钟，一次性）
- 插件设置要新增三个字段：App ID / App Secret / 表格链接（解析出 app_token）
- 插件 `host_permissions` 只加 `https://open.feishu.cn/*`
- App Secret 只存插件本地（`chrome.storage.local`），**绝不进我们的服务端**
- 新建知识点时若单选字段缺选项，插件需 `base:field:update` 权限自动补（参考 feishu-web-clipper）

## 2026-10-23 · 采集两条入口都要做，Chrome 插件先上线

**结论**：两条采集入口**都在产品范围内**——Chrome 插件（先做、主路径）与宿主内置浏览器（紧随其后）。不是二选一。

**原因**

- 插件覆盖「用户在自己浏览器里阅读」，能拿到**选区 + 页面 URL + 标题**，定位精确。
- 宿主内置浏览器覆盖「用户直接在 AI 宿主里打开网页」，省掉装插件这一步，是**不同场景**的补充，不是可选项。
- 两者下游共用同一条处理链（诊断 → 知识点 → 写表），多做一条的成本主要在「怎么拿到选区」。

**实现顺序**

1. **先做 Chrome 插件**：选区天然可得，闭环最容易验证。
2. **再做宿主浏览器**：先测宿主给不给选区——
   - 给选区 → 直接沿用同一套诊断流程
   - 只给整页文本 → 加一步「你想练哪一段」，让用户指认

**影响**

- 首次配置第 5 步「装 Chrome 插件」仍是**必需**（宿主浏览器覆盖不了全部场景）。
- Skill 保留两条入口的分支：默认引导插件；用户明确在宿主浏览器里读网页时走第二条。

## 2026-10-23 · 后端服务是我们的资产，不做纯本地包

**结论**：ReadLoop 保留自己的后端服务（选题 / 组卷 / 判分 / 授权门禁），技术分工与 `Teaming-Bot` 同构：后端在独立仓库，Store 里只放技能包。

**原因**

- 卖包模式下「包被转发」无法在包内解决，只有服务端能识别授权。
- 服务端还承载确定性逻辑（选题与判分不交给模型），这是产品承诺的一部分。
- 用户自带模型与数据，服务端不碰数据，责任边界清晰。

**排除的方案**

- 纯本地包（脚本全在包内）：零运维、离线可用，但无法防复制，且确定性逻辑会暴露在包内易被改。

**影响**

- 部署与运维成本由我们承担（腾讯云单机即可）。
- 三个接口必须实现：`/api/review/today`、`/api/review/submit`、`/api/license/activate`。

## 2026-10-23 · 授权走运行期校验，激活是首次配置第一步

**结论**：卖包模式下用**运行期校验**保护资产——购买发 8 位授权码，Skill 首次配置第 1 步用 `POST /api/license/activate` 换 `host_token`，之后每次请求携带。渠道管控只作辅助，不替代运行期校验。

**原因**

- 要保护的**不是数据**（数据归用户），而是**处理规则**：选题配比、记忆调度、判分口径。
- 规则必须留在服务端；包越薄越好——包被转发也不值钱。
- 分发管控只能管住「包的获取渠道」，管不住「一个包被十个人用同一个服务」。

**影响**

- 首次配置多一步，且是**前置**：没有 `host_token` 后面全调不通。
- `host_token` 从「可选」改回**必需**。
- token 有效期 = 授权期（当前按年），到期返回 402；不按次计费（模型费用本来就是用户出）。
- 激活失败（401 / 5xx）必须在 Skill 里如实反馈，**不允许编一个 token 继续**。

**MVP 不限制激活次数**（2026-10-23 定）

- 同一个授权码可在多台机器重复激活，每次返回新的 `host_token`，旧 token 不强制失效。
- 服务端**只记录激活时间**，用于换机排查；不做设备指纹、不做次数上限。
- 理由：产品价值是「你自己的阅读账本」，一码多用拿到的是对方自己的空表，滥用动机低；早期加限制只会让正常用户（换电脑、公司家里两台）踩坑。
- 触发条件：如果将来出现「一个码激活远超正常次数」，再基于记录加限制。

## 2026-10-23 · 年度授权，非自动续费，不做永久买断

**结论**：出售的是「一年内持续在线的服务」，不是软件所有权。按年买断、**不自动续费**、到期由用户自己决定续不续。不做永久买断。

**原因**

- **收入和成本要匹配**：服务器是每年都在花的钱；永久买断等于收一次、付一辈子，三年后老用户还在吃服务器却没有收入。
- **「永久」是个改不回来的承诺**：这行常见路径是先卖永久、后来被迫转订阅，每次改变都伤用户信任。与其将来改，不如一开始就定年度。
- **习惯类产品，年度重新承诺是好事**：每年续一次等于问用户「还要继续练吗」，愿意续的是真在用。
- **不需要在条款里承诺「永久服务」**，负债期限只有一年。

**为什么用「非自动续费」而不是订阅扣款**

- 保留「买断」的心理：付一次钱管一年，不静默扣款，投诉和退款都少。
- 老用户续费可给折扣（如首年 199、续费 99），续费率更好。

**影响**

- 授权接口返回 `expiresAt`，过期一律 402。
- Skill 遇到 402 只说「授权到期，续费后可继续」，**不清配置、不重装、数据不动**。
- 用户不续费后，账本仍在他自己的飞书表里——这是买断模式最好的一张牌，要写进对外话术。

**已排除**

- 永久买断：现金流好看但负债无限，且与「持续迭代」的定位冲突。
- 自动续费订阅：转化率更高，但会失去「买断」的心理优势，且需要处理扣款失败/退款等一整套流程。

## 2026-10-23 · 以 Skill 包售卖，数据与模型全部归用户

**结论**：产品对外交付形态是**一个 Skill 包**，按包收费。模型 API、多维表格、Chrome 插件、表内数据全部属于用户；我们不提供账号、不做配额、不托管数据。

**原因**

- 用户自带模型 = 模型成本在用户侧，产品不必为额度兜底。
- 数据归用户，合规与责任最轻。
- 卖包是最轻的交付形态，不需要为每个用户运维一套服务。

**影响**

- 首次配置共五步：**激活 / 选模型 / 建表 / 装插件 / 建定时任务**，没有注册登录。
- 真正的资产是**规则与流程**，不是数据（见 [ARCHITECTURE.md](./ARCHITECTURE.md) §2.4）。
- 授权与后端服务的归属见上一条决策。

## 2026-10-23 · 出题模型由用户自带（BYOK），Skill 初始化时选

**结论**：生成题面的大模型由**用户在 Skill 初始化时选择并自带 API Key**（BYOK），存在本地 `~/.readloop/config.json`，随请求传给服务；**服务端不保存、不落库**。测试期推荐 **DeepSeek**。

**原因**

- 原 `coze-coding-dev-sdk` 依赖扣子内网，迁移到腾讯云后不可用，必须换成公网可调的模型。
- 用户自带 Key，模型费用由用户承担，产品不必为额度兜底。
- 模型会迭代、价格会变，写死会让每次换模型都变成一次改造。

**影响**

- 初始化变成三步：**① 选模型 → ② 建多维表格 → ③ 装 Chrome 插件**。
- 配置新增 `model` 段：`provider` / `base_url` / `model` / `api_key`。
- `POST /api/review/today` 请求体带 `model`；接口形状不变。
- 服务端必须校验 `model.base_url`：只允许 `https`，拒绝内网 / 回环 / 链路本地地址（防 SSRF）。
- 日志必须脱敏，任何日志不得出现 `api_key`。

**边界**

- **判分不交给模型**：仍由服务端按题库答案判定，模型只负责生成题面措辞。

## 2026-10-23 · MVP 先跑通豆包工作

**结论**：第一阶段只支持**豆包工作**一个宿主。验收标准是「在豆包里完整跑通一次：初始化 → 拿到今日题 → 逐题作答 → 表里状态真的变化」。Codex / Work Buddy 及其余宿主推迟到第二阶段。

**原因**

- 豆包工作的飞书能力原生内置，不需要 `lark-cli`、不需要飞书应用、不需要额外授权。
- 每多支持一个宿主，就多一套能力差异要处理。先把一条链路打磨稳。
- 能力边界仍需实测（能否发 HTTP、定时任务行为），先用一个宿主收敛不确定性。

**影响**

- Skill 的宿主适配以豆包工作为主路径，其他宿主写在后面。
- 冒烟测试 5 步成为准入条件，未通过不进入下一阶段开发。
- 部署与模型凭证只为单实例设计，暂不做多宿主适配层。

**未决**

- 豆包工作能否执行 shell（决定我们的服务能否被调用）。
- 豆包定时任务能否在任务中调用外部接口。

## 2026-10-23 · 飞书读写交给宿主，我们不做飞书应用

**结论**：多维表格的读写一律由宿主自己的飞书能力完成（豆包原生能力；Codex / Work Buddy 安装 `lark-cli` 并以用户身份登录）。我们不注册飞书应用，也不要求用户把应用加成协作者。服务只做计算。

**原因**

- 飞书 OpenAPI 要求调用方持有应用凭证，但调用方是宿主，不是我们。
- 宿主以用户身份操作，权限天然正确，用户无需授权第三方应用。
- 先例：`teaming-meeting-analysis` 已是同一分工（宿主取妙记，服务做计算）。

**影响**

- 服务接口从「传 app_token 读表」改为「宿主把候选知识点传上来」。
- 鉴权用 `host_token`（接入码兑换），与 teaming 一致。
- `question_id` 改为服务端签名的不透明串，内含知识点与答案，因此服务无需存储任何用户数据。
- 表格结构校验由 Skill 在本地用宿主飞书能力完成。

**代价**

- 宿主必须自带飞书能力；只有 bash 而没有飞书能力的宿主不适用。
- 用户需要安装并登录 `lark-cli`（非字节系宿主）。

## 2026-10-23 · 数据由用户自持，Skill 负责初始化

**结论**：知识库存在每个用户自己的飞书账户里（复制模板得到独立多维表格），我们不托管任何用户数据。Skill 首次运行负责发现并校验这张表，把 `app_token` / `table_id` 记在本地 `~/.readloop/config.json`。

**原因**

- 数据属于用户，产品不承担托管责任，隐私与合规成本最低。
- 与「个人资产」的产品主张一致。
- 用户换设备只需带走一个配置文件，数据本来就在飞书里。

**影响**

- 原先「单 Base + `user_id`」的托管方案作废。
- 用户多做一次初始化：复制模板 → 把表格链接发给 Skill → 用接入码换 `host_token`。
- 服务端只做计算，不直接访问表格，不落地存储用户数据。
- 我们看不到用户数据，无法做运营分析或演示，只能依赖用户反馈。

**代价**

- 用户侧多一步操作，转化会掉，初始化必须做得足够短。
- 宿主必须自带飞书能力（豆包原生，或装 `lark-cli`）。

## 2026-10-23 · 只做 Skill 接入，不做 MCP

**结论**：宿主接入只用 Skill（一份 Markdown + `curl` 调用 HTTP 接口），不做 MCP；定时使用宿主自带的定时任务。

**原因**

- 目标宿主（Claude Code / Codex / Cursor 等编码代理）都具备 bash / curl，一份 Markdown 即可完成接入，零部署。
- MCP 只是同一组接口的另一种壳，当前阶段没有额外收益。

**影响**

- 交付物收敛为三样：HTTP 接口、Skill 文档、插件。
- 身份只能靠配置文件 + 配对码（没有 OAuth 通道）。
- Skill 的代价：凭证写在配置里、模型需自行拼命令与解析 JSON、无法限制目标域名、缺少结构化调用日志。
- **只支持具备代码执行能力的宿主**；面向只有对话能力的普通用户时没有入口，届时再加壳即可，业务逻辑不变。

**未采纳**

- MCP / OpenAPI Action：当前阶段冗余。

## 2026-10-23 · 不自研智能体，改为 Skill + HTTP 接口

**结论**：不开发自己的 AI 助手，而是把能力封装成一组 HTTP 接口，再写一份 Skill 文档（`curl` 调用），装入具备代码执行能力的宿主中。

**原因**

- 宿主本身就是成熟 agent，已具备会话、多端、定时任务、推送与渲染能力。
- 自研等于重做这些基础设施，且拿不到宿主的用户。
- 一份 skill 文档可以多端分发，边际成本极低。

**影响**

- 需要交付：HTTP 接口、Skill 文档（剧本）、身份绑定方案。
- 身份绑定：配置文件 + 配对码（Skills 版本没有 OAuth 通道）。
- 自定义 GPT 的 Action 鉴权为整个 GPT 共用，无法区分用户，不能作为 per-user 身份方案。

## 2026-10-23 · 开通流程全部在 Skill 内完成

**结论**：从选模型、建多维表格、装 Chrome 插件、建定时任务到每日练习，**所有步骤都由 Skill 引导完成**，不依赖外部文档、不要求用户自己找入口。

**原因**

- 用户不该被迫理解系统结构；Skill 就是唯一的交互界面。
- 步骤分散在文档里，用户一定会漏；收进 Skill 才能保证顺序和完成度。

**影响**

- Skill 必须能检测每一步是否真的完成：模型可用、表结构与字段齐全、插件可用、定时任务已创建。
- 任何一步失败都要明确说「卡在哪、下一步做什么」，不允许跳过或假装成功。
- 允许切换飞书账号：表建在用户想用的账号下即可，Skill 只认链接。

**定时任务是配置项**

- 频率：每天 / 每周（指定星期几）
- 时间：任意整点或半点，如 `09:00` / `21:00`
- Skill 直接调用**宿主的定时任务能力**创建（参数：频率 / 时间 / 任务描述），并读回确认；**不假装已创建**。

**待验证**

- 宿主自带的侧边栏浏览器若暴露当前页面内容，可作为 Chrome 插件的替代采集入口。

## 2026-10-23 · 定时只用宿主定时任务，不做兜底

**结论**：只用宿主自带的定时任务触发每日练习。**不自建 cron、不做推送通道、不做飞书卡片。**

**原因**

- 宿主已实现定时，自建一套是重复建设。
- 多一条兜底链路就多一份维护成本和不确定性。

**影响**

- 宿主定时任务不可用 ⇒ 该宿主不在支持范围内，而不是补一套自己的调度。
- 它的执行情况我们无法观测，只能依赖用户反馈。
- 待验证：宿主定时任务能否在任务中调用外部 HTTP 接口。

## 2026-10-23 · agent 是「嘴」，不是「脑子」

**结论**：agent 只负责呈现与表达；对错判定、下次复习时间、状态变更一律由工具返回。

**原因**

- LLM 输出不确定，同一答案可能今天判对、明天判错，会污染记忆系统的数据。

**影响**

- skill 文档必须显式禁止模型自行判定对错、自行估算统计数字。
- 写库只能通过工具，不允许 agent 直接写入。

## 2026-05-08 · 知识点必须写入数据库；系统不能忘记用户基础

**结论**

1. 重点目标是打通「知识点写入数据库」。
2. 系统需要记住用户具备四六级基础，避免给出 `more` 这类过于简单的知识点。
3. 知识点应是从对比结果中提取的**原子级**知识点，而不是照搬「可优化表达 / 遗漏要点」。

**原因**

- 知识点总结刻板、粒度过粗，用户无法据此复习。
- 界面出现了学习类 App 的文字与形式，与产品定位不符。

**影响**

- prompt 中已加入「常见词不提取」规则与词性还原、组合拆分逻辑。
- 用户画像仍未落地（当前靠模型猜难度，而不是知道用户的真实水平）。

## 2026-04-30 · 知识库按记忆规律调度，而非静态收藏

**结论**：知识库是「问题账本 + 练习调度器」，不是给人浏览的笔记本。

**具体规则**

1. 首次出现 → 新建；重复暴露 → 提高练习债务。
2. 做题答对 → 降低练习债务。
3. **真实阅读中再次正确理解** → 比做题答对更强的信号，应更快进入掌握状态。
4. 已掌握 → 从活跃集合移出，保留历史；再次出错 → 重新激活。

**练习原则**（来源：同一文档「什么样的练习最科学」）

- 检索练习 > 重复阅读
- 间隔重复 > 集中重复
- 交错练习 > 同类连刷
- 语境化复现 > 孤立记忆
- 生成式练习 > 纯识别式练习
- 难度控制在「努力后能答对」（目标成功率 70–85%）

**影响**

- 直接决定了 [REVIEW_RULES.md](./REVIEW_RULES.md) 的整套设计。

## 2026-04-21 · 产品定位与 MVP 闭环

**结论**：面向「有一定英语基础、但阅读英文 AI / 产品 / 创业内容仍吃力的中文职场用户」，把用户投喂的文章变成个人训练材料。

**当时的 MVP 闭环**

```text
输入文章链接 / 粘贴正文
→ 提取正文 → 按段落切分
→ 用户选择段落并提交自己的翻译
→ 仅在提交后才生成 AI 参考翻译
→ 对比诊断薄弱点 → 沉淀为知识点
→ 阅读结束后生成少量练习题
```

**影响**

- 「必须在用户提交翻译后才给参考翻译」是一条持续有效的原则。
- 2026-10 的架构调整把入口从「导入文章」改为「划词选中」，但该原则不变。

**已被取代的部分**

- 段落难度评分、推荐练习段、待掌握 / 已掌握双库的早期表述，均已被后续决策取代。
