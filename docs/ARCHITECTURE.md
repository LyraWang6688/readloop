# ReadLoop 产品架构

> 状态：当前有效（2026-10-23 确立）
> 命名：项目由 ReadInsight 更名为 **ReadLoop**，一句话定位是「读的时候暴露短板，AI 助手按时帮你复习」。
> 改名已执行：GitHub 仓库为 `LyraWang6688/readloop`，`package.json` 与插件显示名均已同步。
> 复习与出题的具体算法见 [REVIEW_RULES.md](./REVIEW_RULES.md)。
> 产品定位的历史沿革见 [PRODUCT_POSITIONING.md](./PRODUCT_POSITIONING.md)。

---

## 一、一句话

**把「在真实阅读中暴露的短板」变成一份账本，再让任意一个 AI 助手按记忆曲线每天把短板端回来。**

它不是一个 App，也不是一个翻译器。它是一套规则 + 一份数据，寄生在用户已经在用的软件里。

---

## 二、为什么是这个架构

### 2.1 不自己开发智能体

AI 宿主（豆包工作 / Codex / Work Buddy）本身就是一个成熟 agent，已经具备：对话、推理、多端、账号、**定时任务**、消息推送、界面渲染。

自己做一个 App 等于把这些重做一遍，而且拿不到它们的用户。所以：

```
宿主负责：会话、渲染、定时、推送、多端
我们负责：规则 + 数据 + 采集入口
交界是：一组 HTTP 接口 + 一份 skill 文档
```

### 2.2 我们真正要提供的三样东西

| 层 | 内容 | 形态 | 谁维护 |
|---|---|---|---|
| 契约 | 一组 HTTP 接口 | `/api/review/today`、`/api/review/submit`、`/api/capture` | 我们 |
| 外壳 | 让宿主能用上这组接口 | **Skill（curl 版）** | 我们 |
| 数据 | 用户的知识点账本 | 多维表格 | 我们 |

**Skill 本身不可执行**，它只负责「告诉宿主该干什么」；真正的读写由 HTTP 接口完成——Skill 里的 `curl` 直接打接口，不需要额外的协议层。

### 2.3 一条不能破的边界：agent 是「嘴」，不是「脑子」

| 交给 agent | 必须由工具决定 |
|---|---|
| 题面措辞、讲解语气、每日总结的表达 | 对错判定 |
| 用哪种界面呈现 | 下次复习时间 |
| 怎么追问、怎么鼓励 | 状态与练习债务的变更 |

**原因**：LLM 不确定。同一个答案今天判对、明天判错，记忆系统的数据就会变成噪音。

推论：

1. 判分结果必须来自工具返回值，skill 里要显式禁止模型自行判定。
2. 写库只能通过工具，不允许 agent「觉得自己判对了所以写一条」。
3. 每日总结里的数字必须来自工具返回的 `session_context`，不允许模型估算。

### 2.4 护城河是规则，不是数据

**模型 API、多维表格、Chrome 插件、以及表里的数据，全部属于用户**——我们一项都不拥有。

所以真正的资产是**规则与流程本身**：出题配比、记忆调度、判分口径，以及把它们封装成一套任何宿主都能执行的 Skill 包。

这些规则不是拍脑袋定的——每一条都有记忆科学的出处，见 [MEMORY_SCIENCE.md](./MEMORY_SCIENCE.md)。**「有依据的规则 + 用自己的数据持续校准」才是别人抄不走的部分。**

平台风险的防御方式也随之改变：不是「把数据锁在我们手里」，而是「规则持续迭代 + 换宿主成本极低」。

## 三、总体数据流

```text
┌────────────────────┐
│  Chrome 插件（划词） │  选中一段 → 我翻 + AI 翻 → 三维度对比 → 原子级知识点
└─────────┬──────────┘
          │ POST /api/capture（去重后写入）
          ▼
┌──────────────────────────────────────────────┐
│  多维表格：知识点 / 采集 / 答题 / 今日题        │
└─────────┬────────────────────────────────────┘
          │ 读取到期与新增
          ▼
┌────────────────────┐        ┌───────────────────────────────┐
│  规则引擎（确定性）  │───────▶│ AI 宿主（Skill）               │
│  选题 / 组卷 / 判分  │◀───────│ 豆包工作 / Codex / Work Buddy  │
└────────────────────┘ submit └───────────────────────────────┘
```

**触发方式：只用宿主定时任务。** 用户在自己的 AI 助手里建一次每日任务，宿主按时调用 `review/today`。

不自建 cron、不做推送通道、**不做飞书卡片**。

## 四、宿主接入

### 4.1 接入形态：只做 Skill

> **2026-10-23 决定：只做 Skill 版（curl），不做 MCP。**
> 定时任务使用宿主自带的定时器。

适配对象：**具备代码执行能力（bash / curl）的宿主**，例如 Claude Code、Codex、Cursor 等编码代理。

| 宿主 | 接入方式 |
|---|---|
| 有 bash / curl | 加载 [`skills/readloop/SKILL.md`](https://github.com/LyraWang6688/ai-capability-store/blob/main/skills/readloop/SKILL.md)，零部署 |
| 无代码执行能力 | **不在支持范围**（只做豆包工作 / Codex / Work Buddy） |

**已知限制**：如果产品面向只有对话能力的普通用户，这条路径没有入口。届时不必改业务逻辑——同一组 HTTP 接口再包一层壳即可，但现在不做。

### 4.2 接入三件套

| 组成 | 作用 | 备注 |
|---|---|---|
| HTTP 接口 | `review/today` / `review/submit` / `host/enroll` | 唯一必需项 |
| 外壳 | Skill 文档 | 一份 Markdown，零部署 |
| 数据访问 | 宿主：自己的飞书能力；插件：用户自建飞书应用 | 见 §4.3 |

### 4.3 数据访问：两条写入通道

**服务从不直接访问用户的表。** 写表由两个客户端各自完成：

| 谁写 | 用什么身份 | 写什么 |
|---|---|---|
| **AI 宿主**（Skill） | 宿主自己的飞书能力（豆包原生 / `lark-cli`） | 读知识点、回写复习状态、写 daily_sets |
| **Chrome 插件** | **用户自建的飞书应用**（App ID + Secret） | 写 `capture_events` 与新增的 `knowledge_points` |

> 插件在用户浏览器里，拿不到宿主的飞书能力；而后端按设计不持有任何飞书凭证。所以插件必须用自己的通道——这是本架构里唯一需要飞书应用的地方。

**为什么由用户自建应用，而不是我们的应用**

- 用我们自己的应用 = 我们的凭证能读所有用户的表，等于我们托管了数据，与「数据归用户」冲突
- 用户自建应用（免费）+ 把它加成表格协作者 → 我们始终没有访问权

**插件的首次配置**（一次性，约 10 分钟，由 Skill 第 3 步引导）

1. 飞书开放平台 → 创建「企业自建应用」→ 拿 App ID / App Secret
2. 权限管理 → 开通 `bitable:app`（需要自动补选项时还要 `base:field:update`）
3. 版本管理 → 创建版本并发布
4. 表格右上角 ⋯ → 添加文档应用 → 把这个应用加成「可编辑」
5. 把表格链接 + App ID + Secret 填进插件的设置页

参考实现（同类产品，同一套做法）：
[feishu-web-clipper](https://github.com/EConG37/feishu-web-clipper)、
[job-tracker-extension](https://github.com/Zheyi-D/job-tracker-extension)、
[x-to-feishu-extension](https://github.com/Sharkforever/x-to-feishu-extension)。

> 插件靠 `host_permissions` 可以直连 `open.feishu.cn`，不受 CORS 限制——所以不需要后端中转，写入是实时的。

### 4.4 初始化

Skill 的本地配置 `~/.readloop/config.json`：

```json
{ "base_url": "...", "host_token": "...", "app_token": "...", "model": { }, "schedule": { } }
```

初始化流程：

1. 首次激活：授权码换 `host_token`
2. 选模型（BYOK）
3. 建表 + 配置写入通道：复制模板 → 校验字段 → 引导创建自建应用并加成协作者
4. 装 Chrome 插件（把 App ID / Secret / 表格链接填进插件设置）
5. 建定时任务

细节见 [SKILL.md（Store）](https://github.com/LyraWang6688/ai-capability-store/blob/main/skills/readloop/SKILL.md)。

### 4.5 定时任务的边界

**2026-10-23 决定：只用宿主自带的定时任务**，不自建 cron、不做推送通道、不做飞书卡片。

它的边界：

- 任务由 Skill 下指令、**宿主执行创建**，不需要用户手动配置
- 但执行情况我们无法观测（建没建、跑没跑），只能依赖用户反馈
- 频率与时间是配置项（`schedule` 段）

**频率与时间是配置项**（`schedule` 段）：

| 配置 | 选项 | 默认 |
|---|---|---|
| 频率 | 每天 / 每周（指定星期几） | 每天 |
| 时间 | 任意整点或半点，如 `09:00` / `21:00` | `09:00` |

**不接受兜底方案。** 如果某个宿主的定时任务不可用，那个宿主就不在支持范围内——不补一套自己的 cron。

---

### 4.6 宿主能力边界

不同的 AI 工具能力差得很远，**不能默认「都支持」**。下表是当前认知，未验证的标 ⚠️。

| 宿主 | 飞书读写 | 可执行命令 | 定时任务 | 结论 |
|---|---|---|---|---|
| **豆包工作** | ✅ 原生内置 | ✅ 已验证有 bash + curl | ✅ | **MVP 首选** |
| Codex | ❌ 需装 `lark-cli` | ✅ | ⚠️ 有限 | 第二顺位 |
| Work Buddy | ❌ 需装 `lark-cli` | ⚠️ | ⚠️ | 第三顺位 |

> 只支持这三个宿主，且都是 **PC 桌面版**——这是能安装 Chrome 插件的前提。
> **ChatGPT 网页版、文心、移动端均不在范围内**，不要为它们做适配。

**三条边界结论：**

1. **飞书读写能力是分水岭**。有原生能力（豆包）就不需要任何凭证；没有（Codex / Work Buddy）就必须装 `lark-cli` 并以用户身份登录。
2. **可执行命令是第二道门槛**。没有 shell 就无法调用我们的服务；那种宿主只能由模型自己算，等于放弃确定性——**不纳入 MVP 范围**。
3. **定时任务由宿主创建、宿主执行**，Skill 只负责下指令与参数；我们不建 cron，也不当作送达保证（执行情况无法观测）。

**验证方式**：按 [`doubao-checklist.md`](https://github.com/LyraWang6688/ai-capability-store/blob/main/skills/readloop/references/doubao-checklist.md) 的 5 步冒烟测试逐项确认。**第 3 步（能否发 HTTP 请求）是决定整个分工是否成立的关键。**

## 五、数据层

### 5.1 数据归属：用户自持

> **2026-10-23 修订：数据存在每个用户自己的飞书账户里，我们不做托管。**

| | 做法 |
|---|---|
| 数据在哪 | 用户把模板复制到自己的飞书空间，得到一个独立的多维表格 |
| 我们存什么 | 不存用户数据。服务只做计算，不直接访问表格 |
| Skill 存什么 | `~/.readloop/config.json`：`base_url` / `app_token` / `table_id` / `host_token` |
| 我们负责什么 | 规则、Skill、数据结构设计（模板） |

**选择理由**

- 数据属于用户，产品不承担数据托管责任，隐私与合规成本最低
- 用户换机器只需复制一个配置文件，数据本来就在飞书里
- 与「个人资产」的产品主张一致

**代价**（必须接受）

- 每个用户要自己复制一次模板，多一步初始化
- 宿主必须自带飞书能力（豆包原生；Codex / Work Buddy 需安装 `lark-cli` 并登录）
- 我们看不到用户数据，无法做运营分析或演示，只能靠用户反馈

选项对比（供以后回看）：

| 方案 | 判断 |
|---|---|
| **A. 每人一个 Base（用户自持）** | **采用**：数据归用户，初始化一次 |
| B. 单 Base + user_id（我们托管） | 不采用：与产品主张冲突，且要承担数据责任 |
| C. PostgreSQL | 仅在未来需要跨用户分析与事务时考虑 |

### 5.2 表结构

| 表 | 存什么 | 谁写 | 谁读 |
|---|---|---|---|
| knowledge_points | 状态机：待练次数、连对次数、下次复习、是否活跃 | 采集流程写 / 答题流程回写 | 选题 |
| capture_events | 每次插件采集一条：URL、原文、我的译文、AI 译文、诊断结果 | 插件 | 复盘、迁移识别 |
| practice_events | 每次作答一条：题源、题型、答案、对错、信号强度 | 宿主 | 记忆规则计算 |
| daily_sets | 当日练习包缓存（保证同一天多次调用返回同一套题） | 规则引擎 | 宿主 |

### 5.3 访问层收口

所有读写必须经过 `src/lib/kb.ts`，任何路由不得直接操作表格。这样从多维表格切回 PostgreSQL 时只改一个文件。

### 5.4 已知限制

- 无事务、无唯一索引 → 去重必须「先查后写」
- 无 SQL 聚合 → 选题在应用层计算
- API 有频控 → 批量写入使用 `batch_create`
- 单表记录数有上限 → 达到上限即切换到 PostgreSQL

### 5.5 出题模型：用户自带（BYOK）

题面由 LLM 生成，**模型由用户在 Skill 初始化时选择并自带 API Key**（BYOK），不绑死供应商。

| 项 | 位置 | 说明 |
|---|---|---|
| 模型配置 | Skill 本地 `~/.readloop/config.json` 的 `model` 段 | `provider` / `base_url` / `model` / `api_key` |
| 传输方式 | 随 `POST /api/review/today` 请求体传 `model` 字段 | **服务端不保存** |
| 默认值 | 初始化时推荐 DeepSeek | 用户可改 |

**原则**

1. **选题与判分不依赖模型**——换模型只影响题面措辞，不影响记忆状态。
2. 判分仍由服务端按题库答案完成，**不允许模型自由裁量**。
3. API Key 存在用户本地、随请求传输；**服务端不落库、不写日志**。
4. 换模型不改变任何接口形状。

**安全要求**

- 服务端收到 `model.base_url` 时必须校验：只允许 `https`，拒绝内网 / 回环 / 链路本地地址（防 SSRF）。
- 日志脱敏：任何日志不得出现 `api_key`。

> 现状：原 `coze-coding-dev-sdk` 依赖扣子内网，迁移到腾讯云后不可用；**测试期统一用 DeepSeek**。

## 六、用户路径：全部在 Skill 内完成

> **前提**：宿主为 PC 桌面版（豆包工作 / Codex / Work Buddy），可以安装 Chrome 插件。移动端不在范围内。

**原则：从建表到做题，所有步骤都由 Skill 引导完成，用户不需要看任何外部文档或自己找入口。**

```
前提      已购买技能包，手上有 8 位授权码
第 1 步   激活      授权码 → /api/license/activate → host_token
第 2 步   选模型    用自己的模型 API（BYOK），默认推荐 DeepSeek
第 3 步   建表      Skill 给模板链接 → 用户复制到自己飞书 → Skill 校验表与字段
                   → 引导创建**用户自建飞书应用**并加成表格协作者（§4.3）
第 4 步   装插件    Skill 给 Chrome 商店链接 → 引导安装 → 把 App ID / Secret / 表格链接填进插件
第 5 步   建任务    选频率（每天 / 每周几）与时间（如 09:00），Skill 直接调用宿主能力创建
之后      每日      定时任务触发 → 取题 → 作答 → 回写状态
```

**激活是前置条件**：没有 `host_token`，后面的接口一个都调不通。

**每一步失败，Skill 必须明确告诉用户卡在哪、下一步做什么，不允许跳过或假装成功。**

允许切换飞书账号：表建在用户想用的那个账号下即可，Skill 只认链接。

### 采集入口（两条都做）

两条入口的**下游完全共用**：选中原文 + 我的译文 → 诊断 → 原子级知识点 → 写表。区别只在「谁读网页、怎么拿到选区、用谁的凭证写表」。

| 入口 | 场景 | 说明 | 顺序 |
|---|---|---|---|
| **Chrome 插件** | 用户在自己的浏览器里阅读 | 能拿到**选区 + 页面 URL + 标题**，定位精确；用**用户自建飞书应用**直连写表（§4.3） | **先做，主路径** |
| 宿主内置浏览器 | 用户直接在 AI 宿主里打开网页 | 不用装插件；用**宿主自己的飞书能力**写表 | **紧随其后，同属产品范围** |

**为什么插件先做**

1. 选区天然可得——诊断的最小单位就是「用户选中的那一段」。
2. 不依赖宿主能力，行为完全可控。
3. 先跑通一条，比同时支持两条更快看到闭环。

**宿主浏览器那条怎么做**

先测宿主给不给选区（在宿主里选中一段，问它「我刚才选中的原文是什么」）：

- **给选区** → 直接沿用同一套诊断流程，只是入口不同
- **只给整页文本** → 加一步「你想练哪一段」，让用户指认后再诊断

两条都在范围里，不是待验证后可选项。

## 七、MVP 范围

### 7.0 第一阶段目标：只跑通豆包工作

**当前阶段不追求「支持多个宿主」，只追求「在豆包工作里完整跑通一次」。**

达标标准：在豆包里完成 初始化 → 拿到今日题 → 逐题作答 → 表里 `knowledge_points` 状态真的变化。

Codex / Work Buddy 留到第二阶段，其余宿主暂不考虑。

### 7.1 五步

| 步骤 | 内容 | 验收 |
|---|---|---|
| 0 | 用户复制模板到自己的飞书 → Skill 用宿主飞书能力核对结构 → 接入码换 `host_token` | 四张表字段齐全，可读可写 |
| 1 | 插件 → `/api/capture` → 去重入库 | 同一段再采集不新增，只增加练习债务 |
| 2 | 宿主读知识点 → `POST /api/review/today` → 返回 8 题 | 题目无答案，题型交错 |
| 3 | 宿主答题 → `POST /api/review/submit` → 返回 `updates` → 宿写回表 | 答对间隔推后，答错次日必出 |
| 4 | 宿主定时任务触发 | 连续 7 天不断链 |

### 7.2 明确不做（本期非目标）

指**当前阶段刻意不做**的事，不是永远不做。判断标准：任何一项如果做了会让「在豆包工作里跑通一次完整闭环」往后拖，就不做。

| 不做 | 原因 |
|---|---|
| 多用户注册 / 登录 / 配额 | MVP 是单人验证，账号体系会拖慢闭环验证 |
| 服务端托管用户数据 | 与「数据归用户」冲突，见 §5.1（**每人一个 Base 是已采用的方案，不是不做的项**） |
| ChatGPT / 文心 / 移动端适配 | 只支持 PC 桌面版的豆包工作 / Codex / Work Buddy |
| 「真实阅读中再次译对」的自动识别 | 最值钱但实现最复杂，放第二批 |
| 页面重构 / 旧链路删除 | 先并行跑通新链路，避免边改边坏 |
| 自建 cron / 推送通道 / 飞书卡片 | 触发只用宿主定时任务 |
| 用户自定义模型的前端配置界面 | 服务端默认模型先跑通，接口预留、界面不做 |

### 7.3 验收标准

不是功能数量，而是：**一个人连续用 7 天，每天都能收到题、能做、表里的状态真的在动。**

## 十一、交付与售卖

**对外交付物就是一个 Skill 包。**

| 项 | 归属 |
|---|---|
| 模型 API | 用户自带（BYOK） |
| 数据 / 多维表格 | 用户自己的飞书空间 |
| Chrome 插件 | 用户安装，数据只在本机与自己的表之间流动 |
| **规则 / Skill 包** | **我们**，分发 |
| **后端服务** | **我们**，是我们的资产，不是可选组件 |

**这决定了三件事：**

1. 没有账号体系、没有配额、不托管数据——成本与责任都在用户侧。
2. **后端服务必须存在**：它承担选题 / 组卷 / 判分，也是唯一能识别授权的环节。不做纯本地包。
3. 「包被复制转发怎么办」由服务端兜底，而不是靠包内加密。

**商业模式：年度授权，非自动续费**（2026-10-23 定）

```
出售的是「一年内持续在线的服务」，不是软件所有权
首年付费 → 拿到 8 位授权码 → 激活换 host_token（带 expiresAt）
到期不自动扣款 → 用户自己决定续不续
不续：服务停，但数据仍在他的表里，随时可以导出或自己按文档练
```

**不做永久买断**：永久买断等于「收一次钱、服务到永远」，三年后老用户还在吃服务器却没有收入。
也正因为不卖永久，我们不需要在条款里承诺「永久服务」。

**授权接口**

```
首次配置第 1 步 → POST /api/license/activate → { hostToken, expiresAt }
之后每次请求   → Authorization: Bearer <host_token>
过期          → 402，Skill 提示续费，数据不动
同一授权码    → 可重复激活（MVP 不限次数），只记录激活时间
```

渠道管控只作为辅助，**不能替代运行期校验**——包本身不值钱，值钱的是服务端。
